# 通用游戏联机与 LAN 发现方案

## 本轮实现与目标

本轮交付服务端游戏目录、Steam 资料及图片导入、手动端口配置和客户端选择。所有游戏共用 Nebula TCP/UDP 数据面；通用游戏 `custom` 允许玩家登记本机端口。Minecraft 只保留可编辑的 TCP 25565 预置数据，已移除专用发现协议、组播公告和本机 TCP 代理。

后续目标是玩家在游戏自己的 LAN 列表里发现、加入同房游戏，手动虚拟 IP 作为补充。下述发现方式尚未实现，不出现在当前 API、管理表单或客户端能力声明中；不提前建立 Provider、适配器接口或空实现。

## 发现方式

| 模式 | 后续通用处理 | 必须验证的问题 |
|---|---|---|
| 已知地址单播 | 直接通过 Nebula 访问房内已登记虚拟 IP/端口 | 监听地址、回包端口、动态端口能否由配置描述 |
| UDP 单播查询 | 根据服务端配置向已授权房内成员发送查询，响应交回本机游戏 | 游戏如何取得目标地址；源端口、响应目的地址是否保持正确 |
| UDP 广播 | 在明确的本机接口接收已配置目的端口的发现报文，经 Nebula 单播向房内成员发送，远端在本机游戏可接收的位置交付 | `255.255.255.255` 与子网定向广播、端口独占、Windows/Linux 本机接收行为 |
| UDP 组播 | 按配置加入指定组和端口，用相同的房内单播通道传递；本机注入不得继续扩散到物理网络 | 组地址、网卡选择、TTL、循环报文、源地址与后续连接关系 |
| 响应包含地址 | 在发现后验证游戏实际连接的 IP/端口；仅报文转发不足以判定支持 | 内嵌物理 IP、动态端口、校验和、签名和协议版本；不自动猜测、扫描或开放端口 |

广播和组播只用于发现。实际游戏连接仍须走已授权虚拟地址及 TCP/UDP 端口，不跨房转发，不扩大到物理 LAN 中的其他设备。ARP、以太网广播、非 IP 协议或依赖同一二层网段的游戏不属于当前 Nebula 三层实现的已知能力，须单独验证后决定产品支持范围。

## 配置职责

游戏资料与网络配置分开维护。Steam 仅提供名称、简介和图片，不能据此推断联机端口或发现协议。

后续网络配置拟包含：发现模式、UDP 目的端口、组播组、查询/公告方向、允许的响应端口与端口范围、有效期，以及已经验收的游戏版本和操作系统。网络规则使用服务端版本号并随房间快照同步；客户端只执行自己支持且校验通过的模式，未知模式须明确报告不支持。

通用游戏可由玩家选择已实现的发现模式及端口，仍受服务端相同的端口、流量、报文大小和授权约束。游戏身份不决定代码分支；需要特殊字节解析的协议先记录兼容性缺口，只有在真实样本证明必要时才设计受限、可审查的声明式转换，不在配置中执行脚本。

## 转发路径与边界

候选路径为“本机游戏发现 UDP → 本机发现组件 → 房内 Nebula 单播 → 对端发现组件 → 对端本机游戏”。控制面只下发规则、成员与授权，不中转发现报文或游戏流量；不修改固定 Nebula 的 TUN、握手或 relay，不使用其广播/组播承载全房发现。

发现组件的房内通道须与 RTT 探测分开定额，并明确保留端口。通道报文只携带房间、规则版本、来源成员、原始源/目的端口、有限长度载荷和去重标识；接收端根据实时快照核对 Nebula 来源 IP、成员、规则与有效期，不能信任报文自报身份。首轮原型采用 UDP 载荷上限 1200 字节、每成员每规则每秒 10 包和有界队列；超限丢弃并显示计数，是否调整须以真实游戏报文与 MTU 验证为依据。

仅接收确认为本机游戏产生且匹配配置的报文，拒绝把所在物理 LAN 当作授权来源。每条转发记录最多经过一次房内传递，短期去重缓存和来源标记阻止本机回环及多成员互相重发；规则停用、离房、踢人、证书到期和接口变化时关闭监听、清理缓存与映射。未取得新授权不能延长通道或动态端口的寿命。

关键技术验证是本机交付：普通 UDP socket 重发可能改变源 IP/端口，游戏又可能使用报文源地址建立后续连接。Windows 上端口共享、原始报文交付以及多网卡行为不能由 Linux 结果代替。先在现有权限和固定 Nebula 边界内验证可行路径；如需新驱动、WFP 注入、TUN 扩展或数据面依赖改动，明确列出后另行评审，不静默安装或修改宿主防火墙。

游戏内含地址、签名或随机监听端口时，必须证明查询、响应及实际游戏连接全部成功。若普通 socket 转发无法保持语义，应在客户端标记该模式/游戏暂不支持；不能把“发现包已收到”显示成“LAN 联机已支持”。

## 实施与验收

1. 选取真实游戏报文样本，覆盖固定端口单播查询、广播查询/响应、周期组播公告和携带地址的响应；仅在本机授权测试环境采集，去除身份和会话数据。
2. 在 Windows、Linux 分别验证接收与注入、端口共享、源地址/端口、回包路径和接口选择。完成可行性结论后再确定发现通道协议与 `Game` 配置字段，并同步 OpenAPI。
3. 实现一套由规则驱动的发现组件，接入现有授权与 Stop/Wait 生命周期。增加管理台模式配置和客户端能力说明，兼容性以实际验收结果展示。
4. 自动回归覆盖双成员与三成员、跨房拒绝、伪造来源、回放/重复、超速与大包、失联到期、配置收窄、离房/踢人、睡眠恢复及多网卡切换；流量统计必须来自真实报文。
5. 两台 Windows、两个不同 NAT 下，用至少两款不同发现机制的游戏本体验证“游戏内出现房间 → 点击加入 → 持续游戏 → 撤销断连”。Minecraft 可作为组播公告样本，不作为专用代码分支；如无法通过统一转发完成，记录具体兼容性限制。

在完成第 5 步前，协议模拟器、局域网同网段测试或出现一条公告均不能替代通用 LAN 游戏联机验收。当前已实现操作见 README，实际检查状态单独记录在 `validation.md`。
