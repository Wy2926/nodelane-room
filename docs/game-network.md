# 游戏网络与 LAN 兼容

目标是让游戏看到具有同网段、MAC、广播和组播语义的虚拟局域网。所有游戏统一使用 Ethernet LAN v1，管理员配置网络权限，不保留旧 L3 游戏路径。完整兼容是验收目标，不能仅凭转发组件宣称所有游戏均可联机。操作见 README，实际结果见 [验证记录](validation.md)。

## 组成与选型

```mermaid
flowchart LR
  A[游戏 A] <--> TA[TAP · MTU 1500]
  TA <--> LA[房间授权与帧分片]
  LA <--> N[Nebula · 加密 / 打洞 / 原生中继]
  N <--> LB[重组与房间授权]
  LB <--> TB[TAP · MTU 1500]
  TB <--> B[游戏 B]
```

`internal/lan` 使用标准库处理报文、现有 netlink 配置 Linux TAP、现有 go-winio 与 winipcfg 操作 Windows TAP-Windows6。`engine` 通过固定 Nebula 的公开 `overlay.DeviceFactory` 接入，保持原有证书、加密、打洞、中继和 Stop/Wait 生命周期；没有新增公网监听器或传输 Provider。Windows 依赖独立准备的签名 TAP 驱动，程序不会自动安装。

TAP 直接持有证书分配的 IPv4，以及由该地址导出的 IPv6 ULA 和由 MAC 导出的链路本地地址。只有一张面向游戏的虚拟网卡；帧的 IPv4/UDP 封装直接交给 Nebula，解密后直接交给 LAN 组件，不进入宿主 IP 路由栈。由此避免第二套地址分配、系统内嵌套隧道及路由递归。基础设施继续用原生 Nebula TUN，无需 TAP。

选择 TAP 的原因是 [Wintun](https://www.wintun.net/) 提供 L3 接口，UDP socket 重发无法保留任意 Ethernet/非 IP 语义。[Linux TUN/TAP](https://docs.kernel.org/networking/tuntap.html) 和 [TAP-Windows6](https://github.com/OpenVPN/tap-windows6) 提供系统虚拟以太网入口。[ZeroTier 的协议](https://docs.zerotier.com/protocol/) 同样将传输与虚拟 Ethernet 分层；本项目沿用已有 Nebula 传输。

## 授权与交付

当前数据库结构为 4：`games.network` 保存必需策略，`members.mac` 保存房间绑定，并有同房活跃 MAC 唯一索引。旧 `endpoints` 表、登记接口与客户端本地端口列表已移除；没有旧库迁移、空策略回退或双模式运行。

- `Game.network` 指定版本、广播、组播及附加 EtherType；TCP/UDP 端口仍由服务端配置。端口规则没有条目数或展开数量上限，可用两条区间授权 TCP/UDP 各自的 1–65535；重叠规则和非法端口被拒绝，一般 HTTP 请求体大小限制继续生效。
- 心跳上报 `lan_version` 与实际 TAP MAC。服务端在已有事务锁内绑定设备、检查同房重复 MAC，通过权威快照分发；本机 MAC 尚未确认时拒绝游戏流量。心跳必须声明当前能力版本，缺失即拒绝。
- 外层只开放同房 UDP 4244 帧通道和必要诊断。内层双向校验 Nebula 来源 IP 对应的成员、登记 MAC、IPv4/IPv6 源地址、目的成员、规则版本、房间标识及端口。转发不改写游戏源 IP、端口、目的地址或载荷。
- 单播只交付对应 MAC；广播、组播按当前房间成员复制。ARP/NDP 是必要链路控制，绑定成员地址与 MAC；不桥接物理网卡、不学习其他设备 MAC，不向基础设施泛洪。基础设施 IPv4 诊断使用受限代理 ARP。组播复制不依赖 IGMP/MLD 路由器。
- TCP/UDP 检查目的端口，允许已观察到的授权请求反向回复临时端口。UDP 状态最长 30 秒、TCP 最长 5 分钟，每次仍验证成员与凭据；规则/成员 MAC 改变清空状态。授权基于地址与端口，不识别本机具体游戏进程。
- IP 分片先完整重组再检查端口，再交付原帧，拒绝重叠片与无首片旁路。帧分片带启动随机数、序号、房间摘要和游戏 revision，已完成序号按会话滑动窗口去重。注入与规则发布串行化，旧代次排队帧不能在新快照之后交付。
- 成员授权到最近服务端心跳后 45 秒，并受当前证书和房间截止时间约束；失联不延长。退出、踢人、关房和证书撤销沿用 blocklist 与主动关隧道。端口或发现开关改变须 Stop/Wait 后重建 TAP/探测；正常心跳无需重启。
- LAN 诊断 UDP 4243 通过内存 PacketConn 直接进入 Nebula，不绑定宿主游戏端口；游戏可以使用 UDP 4243。

内存有界：TAP 队列 128 帧、待发队列最多 4096 个分片、同时重组 128 个 Ethernet 帧、64 个 IP 数据报（各不超过 65535 字节/128 片），重组超时 2 秒；反向连接状态最多 8192 条，重复窗口最多 128 个会话、各 4096 个序号。满载丢弃，不通过无界缓存或可靠重传增加排队延迟；极端泛洪和吞吐仍需压力实测。

## MTU 评审

采用 **游戏 TAP MTU 1500，Ethernet 帧按最多 1024 字节拆分**。普通小帧用一个分片，最大 1514 字节的无 VLAN Ethernet 帧用两个；接收齐全才交付。固定大小无需探测预热，直连与 relay 切换时不改变游戏网卡 MTU。

| 方案 | 取舍 |
|---|---|
| 降低游戏 MTU，直接套 VXLAN | Nebula 默认 1300 扣除 IPv4/UDP/VXLAN/Ethernet 的 50 字节，只剩游戏 IP MTU 1250，低于 IPv6 链路最低 1280 |
| 提高 Nebula MTU，依赖公网 IP 分片 | 放大对路径和分片放行的依赖，直连与中继切换可能表现不同 |
| TAP 1500 + 固定大小帧分片（采用） | 保留常见 LAN 报文大小，内部包小且可预测；大帧多一个包，任一片丢失会丢整帧 |
| 动态路径 MTU / 自适应分片 | 可减少包数，但需要路径变更、探测失效和黑洞恢复机制；目前缺少实测依据，暂不引入 |

最大内层包：`1024 + 52 字节帧头 + 20 字节 IPv4 + 8 字节 UDP = 1104`。固定 Nebula 的数据头与认证标签每层各 16 字节，按一层原生 relay 再封装及外层 IPv6/UDP 48 字节计，数据包最大 **1216 字节**，留在 1280 以内。计算假设没有额外 IPv6 扩展头或第三方隧道封装，不替代实际路径、握手及丢包验证。基础设施原生 TUN 继续使用 Nebula 默认 MTU。

[RFC 7348](https://www.rfc-editor.org/rfc/rfc7348.html#section-4.3) 要求 VXLAN 端点不自行分片；这里使用带版本的房间帧格式，不是 VXLAN 线格式。[RFC 8200](https://www.rfc-editor.org/rfc/rfc8200.html#section-5) 规定 IPv6 链路最低 MTU 1280。游戏的大 UDP 数据报由系统产生 IP 分片，本组件完整授权后交付原始分片；不修改 TCP MSS，不叠加可靠传输或包重传。

## 能力与验收边界

| 游戏网络行为 | 客户端支持方式与边界 |
|---|---|
| IPv4/IPv6 TCP、UDP 直连及动态端口 | 配置端口区间；无法预知随机端口时可授权完整范围 |
| 有限广播、子网广播、IPv4/IPv6 组播发现 | TAP 保留原报文，房内复制，后续连接通过同一虚拟网卡 |
| ARP、IPv6 邻居发现、链路本地地址 | 只接受登记成员地址和 MAC，拒绝路由通告等无关控制协议 |
| IPX、非 IP Ethernet、IEEE 802.3/LLC | 显式开放额外 EtherType；`0x8137` 为 IPX，`0` 为 802.3 长度帧。操作系统/游戏须具备相应协议栈 |
| 绑定物理网卡、载荷写死物理地址的游戏 | 须配置游戏选择 TAP；不扫描或改写任意游戏载荷，不能据此保证兼容 |
| VLAN、物理设备桥接、任意地址、特殊 IP 协议 | 当前不提供；附加 EtherType 不能绕过 IP/ARP/IPv6/VLAN 校验。IPv6 支持常见逐跳/目的选项与分片，不承诺所有扩展头组合 |

发布验收须使用两台真实 Windows、不同 NAT 下至少两款不同发现机制的游戏，覆盖“出现房间 → 加入 → 持续游戏 → 撤销断连”；另验证 TAP 安装/卸载、接口优先级、IPv6、睡眠/切网、广播风暴和低 MTU/丢包。反作弊、操作系统移除的协议栈、专用硬件、在线授权或完全封锁 UDP 的网络，不能仅由虚拟局域网解决。模拟帧、Docker TAP 和握手成功均不能替代游戏本体验收。
